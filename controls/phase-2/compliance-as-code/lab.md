# Compliance as Code — Generating Audit-Ready Evidence

## Why This Matters for Nigerian FIs

CBN examiners visit licensed financial institutions periodically. They ask for
evidence — not promises. In a traditional setup, an engineer spends two weeks
compiling screenshots, spreadsheets, and PDFs before each exam. In a
compliance-as-code model, the evidence is generated by a command.

This lab takes the controls you implemented across Course 2 (Kyverno policies,
Falco rules, Network Policies, RBAC, image signing) and produces the evidence
an examiner would ask for.

---

## What You'll Produce

A single compliance evidence report (`compliance-evidence.md`) that contains:

1. **Host OS compliance** — OpenSCAP scan against CIS Linux Benchmark
2. **Kubernetes compliance** — kube-bench audit against CIS K8s Benchmark
3. **Control mapping** — each scan finding mapped to CBN Cybersecurity
   Framework 2018 and NDPA 2023
4. **Pass/fail summary** — which controls pass, which need remediation

---

## Step 1 — Host OS Compliance (OpenSCAP)

OpenSCAP scans the host OS (the Codespaces VM) against the CIS Linux
benchmark. This checks file permissions, user configuration, network
parameters, and audit settings.

### Install OpenSCAP

```bash
sudo apt-get update && sudo apt-get install -y libopenscap8 scap-security-guide

# Verify installation
oscap --version
```

### Run the CIS Level 1 scan

```bash
sudo oscap xccdf eval \
  --profile xccdf_org.ssgproject.content_profile_cis_level1_server \
  --results-arf results.xml \
  --report openscap-report.html \
  /usr/share/xml/scap/ssg/content/ssg-ubuntu2204-ds.xml
```

This produces:
- `results.xml` — machine-readable ARF (Asset Reporting Format)
- `openscap-report.html` — human-readable HTML report

### Extract pass/fail summary

```bash
# Count pass/fail/error results
oscap xccdf generate report results.xml 2>/dev/null | grep -oP '(pass|fail|error|notapplicable|notchecked|informational|fixed)' | sort | uniq -c
```

**Expected output (abbreviated):**

```
    120 pass
     12 fail
     85 notapplicable
      3 error
```

> OpenSCAP will flag failures in a Codespaces environment because the VM
> is optimised for development, not hardened for production. This is expected.
> What matters is that you can generate the evidence and map each finding
> to a regulatory control.

## Step 2 — Kubernetes Compliance (kube-bench)

kube-bench audits the kind cluster against the CIS Kubernetes Benchmark.

### Install kube-bench

```bash
# Download the latest kube-bench binary
wget https://github.com/aquasecurity/kube-bench/releases/download/v0.9.2/kube-bench_0.9.2_linux_amd64.tar.gz
tar xzf kube-bench_0.9.2_linux_amd64.tar.gz
sudo mv kube-bench /usr/local/bin/

# Verify
kube-bench --version
```

### Run the audit

```bash
kube-bench run --targets master,node --config-dir cfg/ --config cfg/config.yaml
```

**Expected output (abbreviated):**

```
== Summary ==
47 checks PASS
12 checks FAIL
3 checks WARN

[FAIL] 1.1.1 Ensure that the API server pod specification file permissions are set to 600 or more restrictive
[PASS] 1.2.2 Ensure that the --basic-auth-file argument is not set
[PASS] 2.1 etcd encryption
[PASS] 5.3.2 Ensure that the cluster has at least one active Network Policy
[FAIL] 5.1.1 Ensure that the default service accounts are not actively used
[PASS] 5.2.1 Ensure Pod Security Standards are set to Restricted
[PASS] 5.2.10 Ensure that containers run as non-root
[PASS] 5.2.12 Ensure that containers drop ALL capabilities
```

> Unlike OpenSCAP, many CIS K8s controls *should* pass if you have completed
> Course 2 Weeks 2–4 (PSA, Network Policies, Kyverno, RBAC). Failing checks
> are real improvement areas.

## Step 3 — Map Findings to CBN/NDPA Controls

Use the provided mapping template to link each scan finding to a regulatory
requirement.

### Open the template

```bash
# The template is at:
#   phase-2/compliance-as-code/cbn-ndpa-mapping-template.csv
cat phase-2/compliance-as-code/cbn-ndpa-mapping-template.csv
```

### What to fill

For each finding from Steps 1 and 2, identify:
1. **Which CIS control** it maps to
2. **Which CBN Cybersecurity Framework domain and control** it satisfies
3. **Which NDPA article** it supports
4. **What technical control** implements it
5. **The pass/fail status from your scan**

### Example mapped entry

| CIS ID | CIS Description | CBN Ref | NDPA Art | Technical Control | Scan Result |
|---|---|---|---|---|---|
| 5.2.1 | Pod Security Standards set to Restricted | CS 3.2 (Least Privilege) | Art 2.4 (Data Segregation) | PSA restricted profile on vuln-bank and vuln-bank-db namespaces | PASS |
| 5.2.10 | Containers run as non-root | CS 3.2 (Least Privilege) | Art 2.4 (Access Control) | Kyverno ClusterPolicy: deny-root-pods | PASS |
| 5.2.12 | Containers drop ALL capabilities | CS 5.1 (Application Security) | Art 2.5 (Data Security) | Containers set capabilities.drop: ["ALL"] in manifest | PASS |
| 5.3.2 | Namespaces have Network Policies | CS 4.1 (Network Security) | Art 2.5 (Data Security) | NetworkPolicy isolating frontend → db, egress restrictions | PASS |
| 4.2.1 | RBAC configured | CS 3.1 (Role-Based Access) | Art 2.4 (Data Segregation) | developer + operator roles with least-privilege bindings | PASS |
| 1.1.1 | API server pod file permissions 600 | CS 2.3 (InfoSec) | Art 2.5 (Data Security) | Host OS file permission check | FAIL |

## Step 4 — Generate the Compliance Evidence Report

Combine everything into a single markdown document.

```bash
cat > compliance-evidence.md << 'EOF'
# CBN/NDPA Compliance Evidence Report

## Environment
- Host: GitHub Codespaces (Ubuntu 22.04)
- Cluster: kind v0.20+
- Scan date: $(date -u +%Y-%m-%d)

## 1. Host OS Compliance (CIS Linux Benchmark)
- Tool: OpenSCAP
- Profile: CIS Level 1 Server
- Result: $(oscap xccdf generate report results.xml 2>/dev/null | grep -oP 'pass|fail' | sort | uniq -c)

## 2. Kubernetes Compliance (CIS K8s Benchmark)
- Tool: kube-bench
- Target: master, node
- Result: $(kube-bench run --targets master,node --config-dir cfg/ --config cfg/config.yaml 2>/dev/null | grep -A5 'Summary')

## 3. Control Mapping
EOF
```

Then append the completed mapping table.

## What a CBN Examiner Would Look For

| Question | Your Answer |
|---|---|
| Are production pods running as root? | No — blocked by Kyverno policy. Evidence: kube-bench 5.2.10 = PASS |
| Are customer data stores isolated from application pods? | Yes — NetworkPolicy allows only frontend:5000 → db:5432. Evidence: kube-bench 5.3.2 = PASS |
| Who can deploy to the cluster? | Operator role. Evidence: RBAC binding attached to ServiceAccount |
| Are images verified before deployment? | Yes — Cosign signature checked by Kyverno. Evidence: verify-image-signature policy in Audit |
| What happens when a container behaves anomalously? | Falco detects and alerts. Evidence: Phase 2 attack exercises |
| Is encryption at rest configured? | etcd encryption = PASS. Evidence: kube-bench 2.1 |
